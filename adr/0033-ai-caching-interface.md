# ADR-0033: AI Library Caching Interface

**Date:** 2026-08-06
**Status:** Accepted

## Context

The webfiori/ai library makes HTTP requests to AI providers (OpenAI, Google, Anthropic, Bedrock). Identical requests—same model, messages, and parameters—often return similar results. Caching these responses can:

- Reduce API costs (AI APIs charge per token)
- Decrease latency for repeated queries
- Enable offline development/testing with cached responses

The library must decide:
1. Whether to depend on an existing cache library (webfiori/cache, PSR-6, PSR-16)
2. How to design the caching interface
3. What responses are safe to cache

## Decision

Define a minimal `CacheInterface` within webfiori/ai with zero external dependencies. Provide an `InMemoryCache` implementation for testing and simple use cases.

### Interface

```php
namespace WebFiori\Ai\Cache;

interface CacheInterface {
    public function get(string $key): ?CachedResponse;
    public function set(string $key, CachedResponse $response, int $ttlSeconds): void;
    public function has(string $key): bool;
    public function delete(string $key): void;
    public function clear(): void;
}
```

### Cache Key Generation

Keys are generated by hashing: `provider + model + serialized_messages + sorted_options`. Developers can override key generation if needed.

### Caching Rules

| Operation | Cached | Reason |
|-----------|--------|--------|
| `chat()` with temperature=0 | ✅ Yes | Deterministic |
| `chat()` with temperature>0 | Configurable | Non-deterministic, but may be acceptable |
| `chat()` with `auto_execute_tools` | ❌ No | Side effects |
| `embed()` | ✅ Yes | Always deterministic |
| `streamChat()` | ❌ No | Streaming incompatible with caching |
| `generateImage()` | ❌ No | Non-deterministic |

### Configuration

```php
$provider->setCache(new InMemoryCache());
$provider->setCacheConfig(new CacheConfig(
    defaultTtl: 3600,
    embeddingTtl: 86400,
    skipCacheAboveTemperature: 0.0, // null = cache all temperatures
));
```

## Alternatives Considered

### Use webfiori/cache

Pros:
- Maintained by same organization
- Includes FileStorage, RedisStorage

Cons:
- Adds dependency, breaking zero-dependency principle
- More features than needed (groups, prefixes, security config)
- Interface doesn't match AI response caching semantics

### Use PSR-6 or PSR-16

Pros:
- Industry standard
- Many existing implementations

Cons:
- Adds psr/cache or psr/simple-cache dependency
- Requires adapting AI responses to PSR item format
- Overkill for the simple get/set needed

### No caching support

Cons:
- Significant cost waste for applications with repeated queries
- Forces every user to implement their own caching layer

## Consequences

### Easier
- Users can plug in any cache backend by implementing a 5-method interface
- Adapters for webfiori/cache, PSR-16, Redis, etc. are trivial (~20 lines)
- Consistent with existing patterns (HttpClientInterface, ConversationStorageInterface)
- Library remains dependency-free

### Harder
- Users wanting advanced features (distributed cache, tags) must implement them
- No out-of-box Redis/Memcached (but InMemoryCache covers testing needs)
