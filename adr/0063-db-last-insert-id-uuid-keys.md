# ADR-0063: Database: `getLastInsertId()` Returns `string|int` and Supports UUID Keys

**Date:** 2026-11-19
**Status:** Proposed

## Context

`Database::getLastInsertId()` (and `Connection::getLastInsertId()` in each driver) is declared `: int`. It is wrong or unusable in these cases:

- **SQL Server** runs `SELECT SCOPE_IDENTITY()` as a separate `sqlsrv_query()` call. That is a new scope, so the value is always `NULL` and the method returns `0` after every insert (webfiori/database#179).
- **SQLite** returns `lastInsertRowID()`. For a table whose primary key is not an `INTEGER PRIMARY KEY` (for example a `CHAR(36)` UUID), this is the internal rowid, a plausible but wrong id.
- **MySQL** `LAST_INSERT_ID()` only reflects `AUTO_INCREMENT` columns. UUID keys are not reported.
- **Tables without an identity column** return `0` (SQL Server) or a rowid (SQLite) with no way to tell them apart from a real id.

UUID primary keys are widely used, so an `int` return type cannot represent the id of the row that was just inserted. The library has no UUID data type; UUID keys are `CHAR(36)`/`VARCHAR(36)` columns or, on SQL Server, `UNIQUEIDENTIFIER` created through raw DDL.

Two related SQL Server bugs touch the same code path (`MSSQLConnection::runQuery()` / `runInsertQuery()`): #178 (a `raw()` INSERT is bound with the parameters of the previous builder insert) and #180 (a defaulted column given by name is added twice). #178 and #179 are fixed together because both depend on deciding which statements are builder inserts.

## Decision

`getLastInsertId()` returns `string|int` on `Database`, `Connection` and every driver.

After a **query-builder insert**:

1. If the table has an identity or auto-increment key, return the generated value as `int`.
2. Otherwise, if the table has a single-column primary key, return the inserted row's key value as `string` (as `int` when the key column has an integer type). This covers keys supplied by the application and keys generated by the server (for example `UNIQUEIDENTIFIER DEFAULT NEWID()`).
3. Otherwise (no primary key, or a composite key), return `0`.

After a **`raw()` insert** the library cannot know the key column, so only the identity case applies: `int` when an identity value was generated, `0` otherwise. On SQLite the driver reads the table name from the `INSERT` and checks with `PRAGMA table_info` whether it has a single `INTEGER PRIMARY KEY`; if not, it returns `0`. If the table name cannot be read (for example a schema-qualified name) it falls back to the SQLite rowid.

The value is reset to `0` before each insert, so it is never carried over from an earlier statement or table.

Driver mechanics:

- **SQL Server:** capture the id in the same batch as the insert and store it on the connection. Use `SCOPE_IDENTITY()` for identity keys. For non-identity keys on builder inserts, use `OUTPUT INSERTED.<pk>` (with `INTO` a table variable when the table has triggers). `@@IDENTITY` is not used because it includes identities created by triggers.
- **SQLite:** for builder inserts, use `lastInsertRowID()` when the key is auto-increment; otherwise return the key from the inserted values, or `0` when none was given.
- **MySQL:** for builder inserts, use `LAST_INSERT_ID()` when the key is auto-increment; otherwise return the supplied key value, or `0` when none was given. A server-generated MySQL UUID default (`DEFAULT (UUID())`) cannot be read back and is out of scope.

`AbstractQuery::setQuery()` clears the stored insert builder, so a statement set through `raw()` is never bound with the parameters of an earlier builder insert (#178). This applies to all drivers, not only SQL Server. On SQL Server a raw insert runs through the generic path with the parameters passed to `raw()`, with `SELECT SCOPE_IDENTITY()` appended in the same batch.

## Alternatives Considered

- **Keep `: int` and add a second method (for example `getLastInsertKey(): string|int`).** Avoids any change for existing callers, as ADR-0020 prefers, but leaves the existing method wrong for UUID tables and gives users two methods that mean nearly the same thing. Rejected in favor of fixing the method in place.
- **Always return `string`.** Simple and uniform, but turns every existing integer id into a string and breaks `===` comparisons and arithmetic. Rejected.
- **Return `int` and `0` for non-integer keys (status quo, fixing SQL Server only).** Does not solve the UUID case. Rejected.
- **`OUTPUT INSERTED.<pk>` for all SQL Server inserts.** Needs the key column, which raw statements do not provide, and fails on tables with triggers unless `INTO` is used. Rejected for identity keys; kept for non-identity keys on builder inserts.
- **`@@IDENTITY` in a separate call.** Also returns identities created by triggers. Rejected.

## Consequences

### Benefits

- UUID-keyed tables get the correct id on SQL Server, SQLite and MySQL (for application-supplied keys).
- SQL Server identity inserts return the real id instead of `0`.
- No stale ids across inserts or tables.

### Trade-offs and compatibility

- Widening the return type is source-compatible for subclasses: an override declared `: int` is still valid, because a narrower return type is allowed. It can break **callers** that pass the result to an `int` parameter under `strict_types`, or that declare `: int` around it. `SchemaChangeRepository` is one such caller inside the library and must be updated. For tables with an identity key, the runtime value is still an `int`.
- ADR-0020 favors backward-compatible minor releases. This change is compatible at runtime for identity keys and only changes behavior where the old value was `0` or a rowid. It is still a type change on a public method, so it needs a changelog entry. It ships in a minor release (2.3), consistent with ADR-0020.
- Raw inserts into UUID-keyed tables return `0`. Callers must supply the key themselves or use the query builder. On SQLite, a raw insert whose table name cannot be parsed still returns the rowid.
- SQL Server returns server-generated UUIDs in upper case, as a `SELECT` does.
- A multi-row builder insert reports the key of the last row. On MySQL, auto-increment keys keep the driver behavior (the first generated id of the batch).
- Composite keys return `0`.
- MySQL server-generated UUID defaults cannot be returned.
